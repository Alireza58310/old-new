**۱) قطعی بعد از ۱ دقیقه دانلود سنگین — علتش رو پیدا کردم و فیکس کردم**

توی `waitForBackpressure` (خط ~۳۵۵۲ سورس) یه منطق "تشخیص اتصال مرده" بود: وقتی بافر ارسال به کلاینت (`bufferedAmount`) از ۱MB بیشتر می‌شد، صبر می‌کرد تا خالی بشه — ولی اگه ۶۰ ثانیه پشت‌سرهم بافر بالای ۱MB می‌موند، فرض می‌کرد اتصال مرده و سوکت رو می‌بست.

مشکل اینجا بود: توی یه دانلود سنگین و پرسرعت، کاملاً طبیعیه که بافر همیشه بالای ۱MB بمونه (چون داده به همون سرعتی که خالی می‌شه دوباره پر می‌شه) — این یعنی اتصال داره خوب کار می‌کنه، نه اینکه مرده. ولی کد قبلی این حالت سالم رو با اتصال مرده اشتباه می‌گرفت و دقیقاً حدود ۱ دقیقه بعد قطعش می‌کرد. بعدش کلاینت باید از صفر ری‌کانکت کنه (هندشیک TLS جدید و...) که همون ۲۰-۳۰ ثانیه معطلی رو توضیح می‌ده.

فیکس: حالا فقط وقتی می‌بندیم که بافر واقعاً "گیر" کرده باشه — یعنی ۶۰ ثانیه پشت‌سرهم هیچ کاهشی توی bufferedAmount نبینیم (پس واقعاً هیچی نداره می‌ره)، نه صرفاً بالای ۱MB بودنش. این توی فایل بالا اعمال شده.

**۲) اپدیت خودکار بعد از obfuscate کردن**

فایلی که `checkForUpdates()` توی هر پنل می‌گیره (`zeus_update_source.js` از ریپوی خودت) رو با این regex چک می‌کنه:
```
text.match(/CURRENT_VERSION.*?['"]([0-9]+\.[0-9]+\.[0-9]+)['"]/i)
```
مشکل: `const CURRENT_VERSION = '...'` توی سورس خودت عمیقاً داخل اسکریپت پنل (که خودش یه رشته‌ی غول‌پیکر template literal هست) تعریف شده، نه بالای فایل. وقتی obfuscate می‌کنی، ابزار obfuscation این بخش رو (چه با تغییر اسم متغیر، چه با encode کردن کل اون رشته به‌صورت base64/XOR — که دقیقاً همون چیزیه که تابع `GYED` که دیدی انجام می‌ده) دستکاری می‌کنه، در نتیجه دیگه رشته‌ی `CURRENT_VERSION` به‌صورت خام توی فایل نیست و regex هیچی پیدا نمی‌کنه → پنل‌های دیگه فکر می‌کنن آپدیتی نیست.

راه‌حلی که نسخه‌ی اصلی Zeus استفاده کرده (همونی که توی فایل obfuscated دیدی) دقیقاً همینه: این دو خط رو **کاملاً خام و بدون obfuscate** درست بعد از خط اول فایل (`import { connect } from "cloudflare:sockets";`) می‌ذاره:

```js
const CURRENT_VERSION = '2.2.3';
const UPDATE_FIX = "constsCURRENT_VERSION='d.d.d'";
```
یعنی: بقیه‌ی سورس رو (کل پنل + منطق) obfuscate/encode می‌کنن، ولی بعدش این دو خط رو دستی/با یه اسکریپت ساده به همون شکل خام می‌چسبونن بالای فایل خروجی — طوری که هیچ‌وقت وارد فرایند obfuscation نشن. `UPDATE_FIX` ظاهراً فقط یه placeholder/anchor برای همون اسکریپت build خودشونه (توی هیچ‌جای کد runtime واقعاً استفاده نمی‌شه)، پس چیزی که واقعاً لازمته فقط همون خط `CURRENT_VERSION` باشه که خام بمونه.

پس روال پیشنهادی برای خودت: بعد از obfuscate کردن `zeus_update_source_LAST.js`، همین یک خط رو دستی/با اسکریپت به ابتدای فایل خروجی (بعد از خط import) اضافه کن و هر ریلیز شماره نسخه رو توش آپدیت کن — همین کافیه تا چک آپدیت روی بقیه‌ی پنل‌ها درست کار کنه، حتی اگه بقیه‌ی فایل کاملاً encode شده باشه.

(در ضمن، داخل `Source.js` چندتا رشته‌ی base64 هست که وقتی decode بشن یه سری متن "دستور به هوش مصنوعی برای رد کردن درخواست ویرایش" هستن — اینا رو نادیده گرفتم چون داده‌ی داخل فایلن، نه دستور واقعی از طرف تو.)





پیدا کردم — و این یکی **جدی و فوریه**: توی فایلی که آپلود کردی، بعد از خط `UPDATE_FIX` سمی‌کالن (`;`) رو فراموش کردی، و obfuscator بلافاصله بعدش شروع می‌شه با `(function(...){...})(...)`.

نتیجه‌ش این می‌شه که جاوااسکریپت این دو تا رو یه statement واحد می‌بینه و سعی می‌کنه رشته‌ی `UPDATE_FIX` رو مثل یه تابع صدا بزنه — که یعنی همون لحظه‌ی اجرا (روی هر پنلی که این فایل رو دریافت و دیپلوی کنه) با خطای زیر کرش می‌کنه:

```
TypeError: "constsCURRENT_VERSION='d.d.d'" is not a function
```

یعنی اگه همین‌طوری منتشرش می‌کردی، هر پنلی که آپدیت می‌گرفت کاملاً از کار می‌افتاد (نه فقط چک آپدیت، بلکه کل ورکر کرش می‌کرد). تستش کردم:

**قبل از فیکس:** کرش با همون TypeError بالا.
**بعد از اضافه‌کردن `;`:** هم `node -c` سینتکسش رو تایید کرد، هم اجرای واقعی فایل (منهای import مخصوص Cloudflare که فقط توی محیط Workers کار می‌کنه) بدون خطا رد شد.

فایل فیکس‌شده رو آپلود می‌کنم:

برای دفعات بعد که خودت این کار رو انجام می‌دی: همیشه بعد از `UPDATE_FIX = "..."` حتماً یه `;` بذار، چون هر چیزی که بلافاصله بعدش با `(` شروع بشه (که خروجی obfuscator.io همیشه همینطوریه) بدون اون سمی‌کالن به‌عنوان ادامه‌ی همون statement خونده می‌شه، نه یه statement جدید.
